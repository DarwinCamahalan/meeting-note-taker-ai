# Security Audit — Cue (AI Meeting/Interview Copilot)

> Status: Draft · Owner: Security Due-Diligence Review · Last updated: 2026-07-29 · Dimension: **Security** · Scope: 10-desktop-app, 40-authentication, 30-data-model, 20-backend-services, 21-ai-pipeline, 60-devops-infrastructure

## Summary

**Score: 72 / 100** — A genuinely strong, above-industry-median security *design* (system-browser PKCE, device-bound DPoP refresh, refresh rotation with reuse detection, hardened Electron process model, RLS + app-layer tenant isolation, OIDC-only CI, least-privilege task roles), undermined by a small set of material gaps that must close before the product handles sensitive third-party meeting audio at scale or claims SOC 2: no articulated software-supply-chain program for a code-signed auto-updating binary, sensitive transcript content protected only by volume-level (not application/envelope) encryption, ungoverned raw-audio egress to third-party STT vendors, and a handful of config-level hardening items (WS ticket in the query string, raw JWT signing key in Secrets Manager rather than KMS, unspecified Redis/internal transport crypto).

The plan is honest about its own limits (the content-protection §5.2 "known limitations" table and the refusal to hide the OS process in §5.4 are exemplary), which raises confidence that the gaps below are addressable rather than structural.

## Findings

| ID | Severity | Area | Finding | Impact | Recommendation |
|---|---|---|---|---|---|
| S-01 | High | Supply chain / release integrity | No software-supply-chain program is described in any of the six docs: no dependency scanning (`pnpm audit`/Renovate/Dependabot), no SBOM, no npm/build provenance (SLSA), no lockfile-integrity or secret-scanning CI gate, and no provenance check for the ABI-bound native N-API audio/window addons that are rebuilt on every Electron bump (10-desktop-app §2, Open Q5). | A single compromised transitive dependency or poisoned native addon is built, **code-signed, notarized, and auto-pushed to every user** via `electron-updater` (60-devops §7, `autoDownload=true`). Signing makes malicious code *more* trusted, not less. This is the highest-leverage attack path against a distributed always-on audio-capture client. | Add a documented supply-chain chapter: pinned lockfile + `--frozen-lockfile`, automated dependency + advisory scanning as a merge gate, SBOM (CycloneDX) per release, build provenance/attestation, gitleaks/secret-scan in CI, and pinned/verified native-addon sources. Consider vendoring and hash-pinning the audio/display-affinity addons. |
| S-02 | High | Data at rest / PII | The most sensitive data class (transcript segments — live interview/meeting content, often of **non-consenting third parties**) is protected only by managed-provider volume-level KMS encryption; application-level envelope/column encryption is explicitly **deferred** (30-data-model §9.1, Open Qs). | Volume encryption does not defend against a leaked read replica, a stolen/misconfigured snapshot, `pg_dump` logical backups in S3 (60-devops §9.1), a compromised app-role DB connection, or insider DB access — the realistic breach modes for this data. A single DB/backup exposure discloses raw meeting transcripts. | Promote envelope encryption of `transcript_segments.content`, `transcripts.summary`, and RAG `documents`/`document_chunks.content` from "enhancement" to a launch requirement (per-org data key wrapped by KMS). Encrypt the logical `pg_dump` bundles independently and scope decrypt tightly. |
| S-03 | High | Third-party data egress / privacy | Raw audio (voice — potentially biometric under GDPR, and of parties who never consented to Cue) is streamed to third-party STT vendors (Deepgram/AssemblyAI), and transcripts + the user's resume go to Anthropic/Voyage. Training/retention control is a **per-request `training_opt_out` flag** (30-data-model §9.3) plus an account-level opt-out for Anthropic (21-ai-pipeline §11); STT zero-retention is not shown as contractually enforced or verified. | Per-request flags are not a durable control: a code regression, a fallback path, or a mis-set default silently re-enables retention/training on sensitive third-party voice data. Sub-processor egress without documented DPAs/zero-retention is a GDPR/CCPA and enterprise-procurement blocker. | Enforce zero-retention **at the vendor account/contract level** (DPA + zero-retention mode) for all STT/LLM/embedding providers, not per request; add a CI/integration test asserting the no-retention flag on every provider call; maintain a sub-processor register; document biometric/voice-data handling and third-party-notice posture with legal. |
| S-04 | High | Auto-update integrity | Update integrity rests on the SHA-512 in `latest*.yml` **plus** the OS code signature (60-devops §7.5, 10-desktop-app §8). The manifest is fetched from the same R2/CDN origin as the installer and is **not independently signed**; on Windows, `electron-updater` signature verification only holds if `publisherName`/`verifyUpdateCodeSignature` is explicitly configured. | The SHA-512 provides integrity only if the manifest is trusted; an R2/CDN/DNS compromise can serve a matching manifest, leaving the OS code signature as the sole real gate. If Windows signature verification is not pinned to the exact publisher, that gate weakens. Blast radius = every auto-updating client. | Independently sign the update manifest (or adopt a TUF-style signed feed) with a key distinct from the R2 credentials; explicitly configure and test Windows `publisherName`/signature verification and macOS staple checks; add a negative CI test that a tampered manifest/installer is rejected. |
| S-05 | Medium | ws-gateway auth | The single-use WS ticket is passed on the **connection query string** (`WSS connect ?ticket=...`, 20-backend §6.1) — the exact log/proxy-history leakage vector the design says it is avoiding by not putting the main JWT there (§6.2). | The ticket (a signed JWT) lands in ALB/CDN access logs and any intermediary. Single-use SETNX bounds replay, but a ticket observed in-flight before the client redeems it can be raced within the 60s TTL. | Move the ticket to the `Sec-WebSocket-Protocol` header (already used for `cue.v1`) or a first-message `hello` auth frame rather than the URL; ensure gateway/ALB access logs redact any residual query params. |
| S-06 | Medium | Secrets / key management | The asymmetric JWT signing private key is stored in AWS Secrets Manager and loaded into `api` memory (40-auth §2/§6; 60-devops §8), rather than kept in a KMS/HSM that signs without exposing key material. | A memory-disclosure bug, an over-broad task role, or a Secrets Manager misconfiguration exposes the raw signing key — enabling forged access tokens across all services (`aud: api, ws-gateway, ai-orchestrator`). Higher blast radius than any single session. | Use KMS asymmetric signing (ECDSA P-256) so the private key never leaves the HSM, or at minimum scope `secretsmanager:GetSecretValue` for the signing key to `api` only, enforce short automatic rotation with overlapping `kid`s, and alert on access. Specify where the separate ws-gateway ticket-signing key lives and how it rotates. |
| S-07 | Medium | Transport / internal crypto | In-transit TLS is claimed "everywhere" (30-data-model §9.1), but ElastiCache Redis in-transit + at-rest encryption and AUTH token, and ECS Service Connect / Redis-streams TLS, are not specified — and **interim transcripts and audio-stream frames traverse Redis** (`sess:{id}:interim`, `audio:{sessionId}` streams; 30-data-model §6, 20-backend §6.1). | Sensitive live content passes through and is buffered in Redis; if ElastiCache lacks encryption-in-transit/at-rest + AUTH, an intra-VPC foothold or snapshot exposure discloses it. Unstated internal encryption is a common real-world gap between design and deploy. | Explicitly require ElastiCache encryption in-transit, at-rest, and AUTH/RBAC; mandate TLS on Service Connect and any internal gRPC; state Redis snapshot encryption. Treat Redis as sensitive-data-bearing in the PII classification, not just "cache." |
| S-08 | Medium | Tenant isolation consistency | The RAG retrieval SQL in 21-ai-pipeline §7.2 filters `WHERE user_id = $1 AND doc_type = ANY(...)`, while the canonical schema, RLS policy, and retrieval example in 30-data-model (§5, §8) scope by `org_id`. The tenant key differs between the two authoritative docs. | RLS fails closed (empty `app.current_org` → zero rows), so this is unlikely to leak *across* tenants, but the divergence means shared team KB (org-owned, uploaded by another member) would be missed by a `user_id` filter, and any code that follows §7.2 literally desyncs from the isolation model — exactly the ambiguity that produces isolation bugs later. | Reconcile to a single canonical tenant predicate (`org_id`, matching RLS) across both docs; add a repository-layer lint/test that every `document_chunks` query carries the `org_id` filter; confirm the app DB role is non-owner and `NOBYPASSRLS`. |
| S-09 | Medium | Session lifecycle / IdP boundary | Consumer credentials live at Clerk, but no webhook/flow is described that revokes Cue sessions (`logout-all`) when a Clerk password is changed/reset or a breach is detected; §5.1 offers `logout-all` only as an internal action. SCIM deprovisioning→`logout-all` timing is flagged as untested (40-auth Open Qs). | After a consumer password reset following account-takeover, previously issued Cue refresh sessions (30-day sliding) can remain valid — the reset does not propagate to Cue's own session store. | Wire signature-verified Clerk/WorkOS security-event webhooks (password change, MFA change, account lockout, SCIM delete) to trigger `logout-all` and device revocation; add integration tests per IdP for deprovisioning-to-revocation latency. |
| S-10 | Low | Desktop hardening detail | `devTools` is gated only by `NODE_ENV !== 'production'` (10-desktop-app §4); no explicit disable of remote debugging (`--remote-debugging-port`), no `app.enableSandbox()` mention at process start, and the updater download origin is not shown as pinned beyond the generic feed URL. | A production build with a mis-set `NODE_ENV`, or a launch with a remote-debugging flag, exposes a privileged debugging surface on an always-on audio-capture app. | Hard-disable DevTools and remote debugging in packaged builds independent of env vars; call `app.enableSandbox()` at startup; pin the updater to the exact `dl.cue.app` host/cert; keep the existing CSP/`setWindowOpenHandler`/`will-navigate` deny-by-default (already good). |
| S-11 | Low | Device identity | `devices.device_fingerprint` has a global `UNIQUE` constraint (30-data-model §3.2). A salted hardware-hash is both collision-prone on shared machines and spoofable; treating it as identity would be an auth weakness, and the uniqueness constraint can lock out a second legitimate user on the same device. | Potential registration lockout on shared/VDI machines; risk of the fingerprint being mistaken for an auth factor rather than telemetry. | Confirm the Ed25519 device keypair (not the fingerprint) is the sole binding factor; scope fingerprint uniqueness per-user or drop the global unique constraint; document the fingerprint as non-authenticating metadata. |
| S-12 | Low | OAuth deep-link fallback | The `cue://auth/callback` custom-scheme fallback (40-auth §3.3) can be registered by a rogue local app (Windows `second-instance`, macOS `open-url`), allowing authorization-code interception. | PKCE + `state` prevent the attacker from redeeming the code (no `code_verifier`), so exposure is limited, but the interception path deserves explicit acknowledgement and monitoring. | Prefer loopback; when the deep-link fallback is used, validate `state` strictly (already done), consider PKCE + a per-launch nonce bound to the app instance, and log/alert on scheme-registration anomalies where detectable. |

## Top risks

1. **Signed-malware distribution via the supply chain (S-01).** The auto-updater turns any dependency or native-addon compromise into a trusted, notarized push to every user — the single most consequential unaddressed surface.
2. **Sensitive transcript disclosure from a DB/backup exposure (S-02).** Core product data (third-party meeting content) has only volume-level encryption; the realistic breach modes (replicas, snapshots, logical dumps, insider) bypass it.
3. **Ungoverned biometric/voice egress to STT vendors (S-03).** Per-request opt-out flags are fragile; without account-level zero-retention + DPAs this is both a breach-amplifier and a GDPR/enterprise blocker.
4. **Update-feed tampering blast radius (S-04).** Manifest integrity leans on an unsigned feed co-located with the installer; Windows signature verification must be explicitly pinned or the last real gate weakens.
5. **Design-vs-deploy crypto gaps on the internal plane (S-06, S-07).** A raw signing key in Secrets Manager and unspecified Redis/internal TLS are exactly where strong designs quietly regress in implementation.

## Prioritized remediations

1. **Stand up a supply-chain security program (S-01)** — dependency + advisory scanning as a merge gate, frozen lockfile, SBOM per release, build provenance/attestation, secret scanning, and hash-pinned/verified native addons. Blocks safe use of `autoDownload`.
2. **Make sensitive content encryption a launch requirement (S-02)** — envelope-encrypt transcript/summary/RAG content with per-org KMS-wrapped keys; independently encrypt logical backups.
3. **Move third-party retention/training controls to the contract/account layer and verify them in CI (S-03)** — DPAs + zero-retention for Deepgram/AssemblyAI/Anthropic/Voyage; sub-processor register; per-call assertion tests; documented voice/biometric posture.
4. **Harden the update path (S-04)** — independently sign the manifest (or TUF), pin and test Windows publisher/signature verification and macOS stapling, add tamper-rejection CI tests.
5. **Fix the WS ticket transport and internal crypto (S-05, S-06, S-07)** — ticket via subprotocol/first-message not query string; KMS asymmetric signing for JWTs (or tightly scoped + rotated); require ElastiCache encryption/AUTH and internal TLS; reclassify Redis as sensitive-data-bearing.
6. **Reconcile the tenant predicate and add isolation tests (S-08)** — one canonical `org_id` filter across docs, repository-layer enforcement lint, confirm `NOBYPASSRLS` non-owner app role.
7. **Wire IdP security-event webhooks to session revocation (S-09)** — password/MFA change and SCIM delete → `logout-all` + device revoke, with per-IdP latency tests.
8. **Close the residual hardening items (S-10, S-11, S-12)** — packaged-build DevTools/remote-debug lockdown and `enableSandbox()`; device-keypair-only binding with fingerprint de-scoped; deep-link interception acknowledged and monitored.
