## Summary

**Score: 68 / 100 — A genuinely above-average reliability design (clear bottleneck taxonomy, a real degradation ladder, admission control, and an honest risk register), undercut by a capacity model that conflates global demand with per-region provisioning, an under-quantified Redis hot-path SPOF, a headline latency SLO that is optimistic and inconsistently measured, and an availability SLO that collides with the no-cross-region-failover residency stance.**

The plan gets the *shape* right: stateless edges vs. a protected stateful core, connection-scaled autoscaling on a custom metric, leased STT pools, a Redis token bucket for Claude admission, a six-rung degradation ladder, and a load-test matrix that asserts on the same dashboards as production. The authors also label nearly every number an ASSUMPTION and flag the load-bearing ones (A9, STT/LLM lead-time, Redis-on-hot-path) as open questions — that intellectual honesty is worth real credit.

What keeps the score in the high-60s rather than the 80s is a set of concrete, quantifiable gaps that *will* bite in production: (1) the concurrency model derives a single global peak (~4,500) and then sizes the fleet from it, but US and EU are separate, region-pinned stacks that cannot share capacity — each must be sized to its own regional peak; (2) the "Redis absorbs the hot path" claim implies ~225k+ per-frame `XADD`/sec at Growth peak against a single regional Redis that also holds the Claude token bucket, sessions, and WS offsets, with failover time never budgeted; (3) the `<1.2s p95` budget is summed from per-stage p95s (not a valid e2e p95), starts the clock at Deepgram `speech_final` (hiding ~200ms of endpointing), and excludes real client-network latency for every user outside US/EU; (4) the 99.9% availability SLO is mathematically incompatible with a design where a single regional outage drops all of that region's users to snapshot-restore RTO with no failover.

## Findings

| ID | Severity | Area | Finding | Impact | Recommendation |
|---|---|---|---|---|---|
| SR-01 | critical | Redis / hot path | "Redis absorbs the hot path" + per-frame `XADD audio:{sessionId}` (backend §6.1) means ~4,500 sessions × ~50 frames/s ≈ **225k audio `XADD`/s at Growth peak** (≈2M/s at Scale), *plus* `XREADGROUP` consumers, cue `XADD`, the account-level Claude token bucket, entitlement cache, WS offsets and presence — all on a single logical regional Redis. Ops rate is never modeled; failover time is never budgeted. §9 flags Redis-on-hot-path but does not quantify it. | A single regional Redis is the true binding constraint and the largest in-region SPOF. A cluster failover (10–30s) stalls **every** live session in the region simultaneously; a hot-key or memory-pressure event degrades all cues at once. The "gateway is cheap to scale" conclusion is misleading because the gateway's scaling just multiplies Redis load. | Model Redis ops/sec explicitly per scenario. Consider batching audio frames before `XADD` (e.g. 100ms micro-batches) or bypassing Redis for the raw audio path (direct gRPC to orchestrator, Redis only for resumable cue/transcript offsets). Separate the token-bucket / counters Redis from the audio-stream Redis. Add a Redis-throughput + failover test to the *core* load suite (§8), not just a GameDay. Budget and publish the failover-induced live-path stall. |
| SR-02 | high | Capacity model | The model computes a **global** average (744) and **global** peak (~4,500 via A4=6×), then sizes ws-gateway tasks / STT ceiling / TPM from that single global number (§3.2–3.6). But US and EU are separate stacks with region-pinned users and **no cross-region failover** (§4). Each region must be provisioned for its own regional business-hours peak, and the two stacks cannot lend each other capacity. | Systematic under-provisioning. Summed regional peak provisioning exceeds the global-peak figure the fleet is sized to; the STT lease pool and Anthropic quota are also drawn per region. The "8–10 tasks at Growth" and "~11,250 STT streams" figures are global-demand numbers masquerading as provisioning targets. | Re-derive capacity **per region** from each region's user split and local business-hours curve, not from a smoothed global average. State the US/EU split assumption explicitly. Size each region's ws-gateway fleet, STT lease pool, and Claude quota to its own regional peak + headroom. |
| SR-03 | high | Latency SLO | The `<1.2s p95` is derived by **summing per-stage p95s** (pipeline §4 → 900ms; obs §6 → 1130ms), which is not a valid end-to-end p95 (correlated tails under load/provider degradation push e2e ≥ the sum). The pipeline budget starts the clock at Deepgram `speech_final`, which fires **~200ms after true utterance end** (`endpointing=200`), so it excludes the endpointing wait the arch doc *does* count. Client→edge is budgeted at 15/45ms assuming a nearest regional edge — false for every user outside US/EU (APAC/LATAM RTT 150–250ms). | The headline SLO is optimistic and measures a different thing in each doc. Obs §6 sums to 1130ms — <70ms margin to the 1200ms cap, so any single correlated hiccup breaches. The marketed latency is a server-controllable p95, not the latency a large fraction of real users experience. | Publish one reconciled e2e budget with an explicit measurement start point (true utterance end, including endpointing). Validate e2e p95 empirically (§8 ramp), not by summing stage p95s. Separate "server-controllable" from "user-network" latency in the SLO definition *before* GA, and state the experienced-latency degradation for non-US/EU users. |
| SR-04 | high | Availability / DR | The 99.9% availability SLO (obs §9, ~40 min/28d) coexists with a design where a full regional outage drops **all** of that region's users to **snapshot/restore RTO** with no cross-region failover, by residency choice (§4, §9-risk-4). Redis/Aurora primary failover, and the DR RTO itself, are cited but never quantified against the budget. | A single multi-hour regional DR event annihilates the annual error budget for that region's users. A user's effective availability is capped by one region's availability with zero failover headroom — 99.9% is not achievable for a live-meeting product under this posture without an in-region multi-primary story. | Either (a) reconcile the SLO down to what single-region-no-failover can actually deliver and state it honestly, or (b) design an in-region (or in-EU second-region) hot-standby for the live control plane. Quantify Aurora/Redis failover time and DR RTO/RPO and subtract them from the published budget. |
| SR-05 | high | Anthropic quota | The Claude admission token bucket is described as **account-level** but lives in **per-region Redis** (§2.3). Anthropic RPM/TPM limits are typically per-org/account (global). Two region-pinned stacks each drawing from a shared account quota with no cross-region coordination can jointly exceed it and trigger `429/529` storms — precisely the failure the bucket exists to prevent. Growth-scale resolution (per-region sub-accounts?) is not stated; only "multi-account at Scale" is mentioned. | The rate-limit safety valve is not actually global. Under a coordinated US+EU peak, admission control on each side believes it has headroom while the account is already at its ceiling → visible cue stalls exactly when load is highest. | Provision **separate Anthropic orgs/keys per region** (so per-region buckets map to per-region quota) and state it, or implement a genuinely global (cross-region) token bucket. Do the same for STT concurrency ceilings. Add this to the Claude-429-storm load test. |

Poor recall = ungrounded or missing cues; latency spikes = blown budget hop. | Validate filtered-HNSW recall AND latency under a realistic multi-tenant corpus (add a recall assertion to the pgvector load test, not just p99). Plan per-tenant partial indexes or a partitioned `document_chunks` before Growth, not "at Scale". Consider raising `ef_search` with a filter-selectivity-aware policy. |
| SR-07 | medium | ws-gateway sizing | A9 (**2,500 relay connections per 4vCPU/8GB task**) is unvalidated and drives all gateway sizing (§3.3, §9-risk-1, honestly flagged). The doc frames the limiter as "CPU-bound on framing," but the real per-connection cost is the downstream Redis `XADD` rate (see SR-01) and FD/memory, not framing CPU. | If A9 is 2× optimistic, the fleet doubles; if the true limiter is Redis throughput rather than per-task CPU, adding tasks doesn't help. Instrument the *Redis-side* cost per connection in the soak, not just task CPU/memory. Report conns/task at the point Redis latency (not CPU) degrades. |

| SR-11 | medium | SLO measurability | The cue-latency SLO "excludes user-network-bound outliers" (obs §9) but the split point to attribute client vs. server latency **does not exist yet** (obs open-Q3). ## Top risks

1. **Single regional Redis on the hot path (SR-01).** Per-frame `XADD` at ~225k+ ops/sec at Growth peak, co-resident with the Claude token bucket, sessions, and WS offsets, with an unbudgeted failover that stalls every live session in the region. This, not the gateway, is the real scaling wall — and it is the closest thing in the design to a single-event outage.
2. **Capacity model sized on global demand, not per-region (SR-02).** Two region-pinned, non-failover stacks cannot share capacity; sizing the fleet, STT pool, and TPM from a single smoothed global peak systematically under-provisions each region.
3. **The headline `<1.2s p95` is optimistic and inconsistently measured (SR-03).** Summed-p95 methodology, clock started after endpointing, and client network excluded — with <70ms modeled margin. Real experienced p95 for global users is materially worse than advertised.
4. **99.9% availability is incompatible with no-cross-region-failover + snapshot-restore DR (SR-04).** One regional DR event blows the annual budget for that region's users.
5. **Anthropic account quota is global but admission control is per-region (SR-05).** The rate-limit safety valve doesn't actually coordinate across the two stacks, so it fails exactly at coordinated peak.
6. **pgvector filtered-HNSW recall/latency at multi-tenant scale (SR-06)** — unvalidated on the one axis (recall under selective filter) that most affects cue grounding.

---

## Prioritized remediations

1. **Quantify and de-risk Redis (SR-01, SR-07, SR-10).** Model ops/sec per scenario; batch or bypass Redis for raw audio; split the counters/token-bucket Redis from the audio-stream Redis; add Redis throughput + failover to the *core* load suite; instrument per-connection Redis cost in the WS-soak. Blocking for any capacity commitment.
2. **Re-derive capacity per region (SR-02).** State the US/EU split; size each region's gateway fleet, STT lease pool, and Claude quota to its own local business-hours peak + headroom; correct the scenario table to show per-region provisioning.
3. **Reconcile availability posture with the SLO (SR-04).** Quantify Aurora/Redis failover and DR RTO/RPO; then either lower the published SLO to what single-region delivers or fund an in-region/second-EU hot-standby for the live control plane.
4. **Publish one reconciled, empirically-validated latency budget (SR-03, SR-11, SR-12, SR-14).** Single canonical table; explicit start point at true utterance end (including endpointing); separate server vs. client-network segments and build the trace split point *before* committing the SLO; fold cold-cache cues into the reported p95; validate e2e p95 by measurement, not summation.
5. **Make Claude/STT admission genuinely regional or global (SR-05).** Separate Anthropic orgs/keys per region (mapping per-region buckets to per-region quota) or a cross-region global bucket; extend the 429-storm test to the two-region case.
6. **Validate the pgvector filtered-ANN path (SR-06).** Add a recall-under-tenant-filter assertion; plan per-tenant partial/partitioned indexes for Growth, not Scale; adopt a selectivity-aware `ef_search`.
7. **Harden the Postgres connection tier (SR-08).** Specify prepared-statement handling under transaction pooling, assert `SET LOCAL` runs in-transaction (RLS correctness test), and make PgBouncer HA in the topology.
8. **Pin one embedding model end-to-end (SR-09).** Reconcile doc names, confirm the query/doc embedding space is shared, and add a guard test.
9. **State the live-backpressure accuracy trade-off (SR-13)** and quantify the low-bitrate STT accuracy hit before finalizing the shed policy.
