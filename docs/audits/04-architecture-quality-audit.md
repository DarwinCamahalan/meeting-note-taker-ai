## Summary

**Score: 78 / 100 — Architecturally strong and unusually well-operationalized, but held back by several cross-document contradictions in a plan that explicitly promises "contracts before code / single source of truth," and by one hot-path transport choice that sits in tension with the product's defining latency SLO.**

This is a mature, senior-level architecture. The service decomposition is principled (stateless edges / stateful core, realtime path deliberately bypassing the BFF), the ADRs are honestly argued with real alternatives and trade-offs, and the house code-splitting law is genuinely machine-enforced (max-lines 700, `eslint-plugin-boundaries` encoding the layering, renderer→main import ban, `no-explicit-any: error`). The IPC/WS contract design (typed `contextBridge`, discriminated-union `ClientMsg`/`ServerMsg` in `packages/types`, zod-at-boundary, no generic "invoke arbitrary" channel) is exemplary. Testing rigor is above typical for the stage: a content-protection invisibility matrix as a release gate, a k6/Artillery WS load gate bound to the p95 SLO, Pact + zod round-trip contract tests. Versioning and idempotency are solid (URL `/v1` with N/N-1 WS negotiation, `Idempotency-Key` with conflict detection, webhook dedupe on `event.id`).

The deductions are concentrated in three places: (1) the authoritative architecture doc and the backend-services doc **contradict each other** on the single most latency-sensitive edge (`ws-gateway` ↔ `ai-orchestrator`: "gRPC/WS" vs "Redis streams"), and that edge is under-accounted in the latency budget; (2) three separate contradictions about **what actually ships in v1** (billing-webhooks as a service vs a module; `apps/api` vs `services/api`; `ai-orchestrator` as NestJS vs lean bespoke; two divergent `tsconfig.base.json`); and (3) some **stage-inappropriate breadth** (a standalone `entitlements` service, ClickHouse, dual-STT failover, and multi-region residency all committed at v1) applied inconsistently against the plan's own "extract when volume warrants" principle. None are showstoppers, but the contradictions must be reconciled before code is written, because each one is a fork that two teams will resolve differently.

## Top risks

1. **Unresolved + under-budgeted hot-path transport (A01).** The docs disagree on `ws-gateway`↔`ai-orchestrator`, and the Redis-Streams option's latency is not represented in the < 1.2s budget. This is the single most consequential open item for the product's core promise.
2. **Three "what ships in v1" contradictions (A02, A03, A04) plus dual tsconfig (A05).** In a plan that sells "contracts before code / single source of truth," these are forks that two teams will resolve differently, and they touch deploy surface, hot-path service structure, repo layout, and the TS baseline.
3. **No end-to-end latency gate on real hardware (A07).** The defining SLO is validated only per-layer; a client- or relay-side regression can ship silently.
4. **Stage-inappropriate breadth applied inconsistently (A06).** ClickHouse, dual-region residency, dual-STT, and a standalone entitlements service are day-1 commitments that raise ops/COGS ahead of PMF, and the "extract later" rule is not applied evenly.
5. **WebSocket congestion-control gap (A08).** The largest technical unknown behind an otherwise-sound transport decision remains a to-do "before GA."

## Prioritized remediations

1. **Resolve the hot-path transport (A01).** Choose gRPC-streaming vs Redis Streams for `ws-gateway`↔`ai-orchestrator`; make 02 §3/§4 and 20 §1/§2/§6 agree; add explicit per-hop budget lines (including the cue return path) and an empirical validation task. Close backend Open-Q #1.
2. **Reconcile the v1 topology contradictions (A02, A03, A04).** One canonical statement each for: billing-webhooks (module-in-`api`), `ai-orchestrator` structure (lean per ADR-002), and the `services/api` path. Propagate fixes across 02/03/13/20.
3. **Unify the TypeScript baseline (A05).** Single `packages/config/tsconfig.base.json`; root extends or is deleted; reconcile module resolution and strict-flag set; update 03 §3.1.
4. **Add the end-to-end latency release gate (A07).** Staging harness: fixed utterance → first painted token on representative hardware, wired into the existing load-test gate; own the client-side budget split.
5. **Right-size v1 and apply "extract later" consistently (A06).** Reconsider standalone `entitlements` for v1; defer ClickHouse and eu-west-1 until a concrete driver exists; gate dual-STT behind a resilience milestone. Document each extraction/enable trigger.
6. **Spike WebSocket resilience before locking the transport (A08).** Lossy-link test matrix; specify the Opus adaptive-bitrate ladder and the shed-policy accuracy impact; keep WebRTC as documented escape hatch.
7. **Enforce the DTO generation direction (A09).** Codegen `packages/types` from `api` Zod schemas in CI with a diff gate; delete "mirror" language.
8. **Tighten remaining contract/coupling nits (A10, A11, A12).** Expose the single schema via `@cue/core` not `api`; constrain `sampleRate` and document seq-wrap/authority; correct the Node-version claim.
